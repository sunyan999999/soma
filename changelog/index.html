    [2.0.37] — 2026-11-20¶

    语义三元组的 kind（事实 / 关系）：注入按用途过滤，图扩展不受影响。

    背景¶

    下游 1.5 万条 wiki 关联图落在 namespace='' 里，include_global 一开就把 用户情节记忆挤出 70%（192 → 58），而分数面板看不出来（wisdom 77.6 → 77.6）。

    他们用 namespace='wiki_graph' 隔离修好了，但那次修复依赖「写的人记得传 namespace」—— 漏一次就会复发，而且仍然静默。

    kind 把这件事从「靠约定」变成「结构上可过滤」。

    ★ 设计：kind 只管注入，不管扩展¶

    语义库有两条完全独立的消费路径：

    路径 入口 用什么 是否受污染
    图扩展 _expand_via_semantic_graph → expand_query_terms 进程内 NetworkX 图 ❌ 只用节点名
    知识注入 MemoryCore.query → query_by_keywords SQL ✅ 污染只在这里

    所以 kind 只影响注入。与 namespace 互补：namespace 管「谁能看见」， kind 管「这条用来做什么」。

    Schema¶

    ALTER TABLE semantic_triples ADD COLUMN kind TEXT NOT NULL DEFAULT 'fact';
CREATE INDEX idx_semantic_kind ON semantic_triples(kind);

    幂等迁移，旧库自动补列，已有行全部 'fact'。

    取值不锁死：fact / relation 是约定值，也接受 rule / preference 等 自定义字符串。

    API¶

    remember_semantic(..., kind="fact")        # 四层透传
query_by_keywords(..., include_kinds=None) # None = 不过滤
SOMAConfig.semantic_inject_kinds = ("fact",)   # None = 回到 2.0.36

    ⚠️ 默认行为变化¶

    MemoryCore.query 默认只注入 kind='fact'。

    受影响的一类：把导航边写在 '' 且依赖它被注入的下游 —— 他们的注入 结果会变（导航边消失）。这是预期修复，但发布说明必须写清楚，并给出 回滚开关 SOMAConfig(semantic_inject_kinds=None)。

    迁移工具¶

    soma.reclassify_semantic_kind(dry_run=True)    # 默认只预览
soma.reclassify_semantic_kind(dry_run=False)   # 自动备份
soma.rollback_semantic_kind(backup_path)
soma semantic-kind [--apply] [--rollback PATH]

    默认规则：namespace 含 graph → relation，其余不动。 '' 里混进的导航边需要传 predicate_relation=["关联", "参考"] 这类规则 —— 那里本该只放事实，混进去说明写入方已违反约定，工具不替你猜。

    ★ 修复 1：预热 close() 会打死共享实例（下游直接崩）¶

    run_multi_benchmark 在预热结束和每轮结束时都会 agent.close()。 但下游的 agent_factory 返回的是进程级共享实例（全站共用一个 SOMA）， 于是共享的 SQLite 连接被关掉：

    为什么默认不关：不关最坏是多留几个实例（进程退出即回收）， 关错是直接崩 —— 代价不对称。自己每次新建临时实例的调用方 （包括 CLI）显式传 True。

    ON episodic_memories(user_id, agent_id);

    与「在 SQL 里写 INDEXED BY」相比，这样不依赖计划器统计，也没有「索引被删就 直接报错」的硬绑定。实测在先有数据、后补索引的升级路径下（接入方的真实 形态），单加这条索引即可让计划器自觉选对，不需要 ANALYZE。

    老库由 EpisodicStore 构造时执行 _create_table 自动补上，接入方无需手工迁移。 接入方此前为绕过该问题手工建过同名索引 —— IF NOT EXISTS 会直接命中，不重复建。 原有三个单列索引保留（只带 user_id 或只带 agent_id 的查询仍走它们）。

    • skills 表同源问题一并修（收益量级小，为一致性）—— skills 同样有 idx_skill_user / idx_skill_agent，其去重查询也是 user_id + agent_id。 实测 2 万行时 2.2ms → 0.02ms；真实部署里技能表远小于记忆表，绝对收益在 0.1ms 量级。加它是为了避免留下「记忆表修了、技能表没修」的半截状态。

    说明¶

    • 带 group_id 时子句是 (agent_id = ? OR shared_group_id = ?)，OR 条件用不上 单索引，本索引覆盖不到 —— 那条路径仍由计划器决定。
    • 本版不改任何 SQL 语义：所有查询的 WHERE 条件与原版逐字一致，只是让它们有 正确的索引可用。
    • 不需要重装依赖时用 --no-deps；本版未新增第三方依赖。

    [2.0.18.2] — 2026-09-14¶

    接入方在 2.0.18.1 复验里追问出来的三项缺陷修复版（一条 P0 召回、一条 P0 跨用户 隔离、一条 FTS5 检索性能）。内部复验中间版本，未单独对外发布（见 2.0.18.3 说明）。

    修复¶

    • 【P0】向量通道是「检索后过滤」——多租户下对多数用户等于失效 —— query_by_vector 先全局取 fetch_k = top_k * 3 条候选，再由调用方按 mem.user_id != user_id 逐条剔除。单个用户的记忆占全库比例很低时，这 3×top_k 条候选里往往一条都不属于该用户，于是向量通道返回空。它是 RRF 融合里的主通道 （权重 2.0，关键词通道 1.0），而关键词通道本来就是 SQL 前置过滤 （AND t.user_id = ?）—— 两条通道时机不一致正是缺陷根源。

    接入方的分布（27,008 条 / 130 用户，中位用户 17 条 = 0.06%）下，取 45 条候选的 期望命中不足 0.05 条；我们按同样形态合成 1,040 条 / 42 用户的库复现，top_k=10 只召回 1 条（同库的关键词通道返回 5 条，正常）。

    max_age_days 时间窗是同一类缺陷，一并修：窗口内的条目同样会被全局候选挤 出去，原先也是取 top_k 条再按时间剔除。

    现在隔离与时间条件下推给 similarity_search，在该条件下的子集内做精确 top-k （_exact_filtered_search）。关键词通道与向量通道的过滤时机至此一致。

    顺带：这条修复在真实分布下比 v2.0.18.1 还快 —— 前置过滤路径不做那次全表 COUNT，2137 条的用户实测 18.7ms，而同库的无过滤 faiss 路径是 46ms。

    • FTS5 关键词通道的查询计划退化 —— 每次检索固定付几十毫秒 —— 接入方在复验里报「FTS5 比 LIKE 慢一倍」，怀疑关键词通道是负优化。实测复现并 定位到不是 FTS5 本身慢，是 SQL 写法：
    -- 慢：SQLite 选成「t 驱动 → 逐行去 FTS 虚拟表探」
SELECT t.* FROM episodic_memories t
INNER JOIN episodic_fts fts ON t.rowid = fts.rowid
WHERE episodic_fts MATCH ? AND t.user_id = ?

    带 user_id 时该用户有多少行就探多少次 FTS 虚拟表，代价与命中了多少条无关。 本地 27,000 条 / 130 用户实测（中位数）：

    场景 JOIN 写法 子查询写法 倍数
    稠密命中（37%） 137.71ms 16.53ms 8.3×
    稀疏命中（命中 0 条） 38.57ms 0.45ms 86×
    LIKE 对照 0.36ms 0.24ms —

    稀疏那行是关键：一条都没命中仍要固定付 38ms。现改为把 FTS 命中物化成 rowid 列表再比对（WHERE t.rowid IN (SELECT rowid FROM ... WHERE ... MATCH ?)）， 执行计划变成 LIST SUBQUERY（必要时带 bloom filter），仍走 idx_episodic_user：

    SELECT t.* FROM episodic_memories t
WHERE t.rowid IN (SELECT rowid FROM episodic_fts WHERE episodic_fts MATCH ?)
  AND t.user_id = ?

    同一改写应用到另两个同类调用点：memory/consolidation.py 的巩固候选召回、 memory/semantic.py 的三元组召回（semantic_fts 由触发器维护、显式写入 rowid，与主表 rowid 同样等价）。三处语义均不变 —— episodic_fts 是 content='episodic_memories', content_rowid='rowid' 的 external-content 表， fts.rowid 与主表 rowid 本就等价。

    • 【P0】自主目标来源不按用户过滤 —— 属于 2.0.18.1 那个跨用户泄漏的同类 —— GoalGenerator 的四个来源里有三个不做用户过滤（_from_stale_states、 _from_pending_plans、_from_buried_memories），第四个读的是进程内观测值 hub.last_conflicts。这些来源生成的 goal 文本直接内嵌记忆原文 （mem.content[:40]、evidence [:60]），随后被 BackgroundRunner.run_once() 拿去 run_autonomous() 执行 —— 多租户下等于把别人的记忆端到自主循环面前。

    store 层早就支持 user_id（query_by_filters / query_by_context_type 的 签名里都有，docstring 写明「多租户部署必须显式传入」），断点只在 GoalGenerator 没往下传。现在四个来源、门面 generate_goals() / run_self_directed()、 以及 BackgroundRunner 全链路按用户切分：run_once() 为本轮每个目标用户各生成 一轮目标，推进记录里带 user_id。

    目标去重键同时带上用户前缀。stale_state:{id} / conflict:{a}|{b} 用的是记忆 id，本就全局唯一；但 plan:{problem[:60]} 用的是计划文本前 60 字 —— 两个 用户写下同样的计划文字就会撞成同一个 key，于是 A 推进过的目标会把 B 的同名目标 错误地去重掉（跨用户串扰，方向是漏报而非泄漏，但同属「user 维度缺失」）。留空 不加前缀，单租户行为与已存的旧记录都零变化。

    新增 autonomous_background_user_ids 配置（留空 / "*" 自动枚举轮转 / 逗号分隔 列表）与 autonomous_background_max_users_per_tick（每 tick 上限，游标轮转 —— 用户按条数降序，不轮转会永远只服务头部那几个）。

    未配置时的 fail-safe：「未配置」和「真的是单租户」是两回事。留空时若库里 确实有多个用户，_target_users() 直接返回空列表（本轮不产出目标）并记 status()["last_skip_reason"]，而不是静默混合 —— 宁可漏跑，不可泄漏。单租户库 （只有一个用户或全空串桶）不受影响，仍是原语义。

    说明¶

    • 为什么不用 faiss 的 IDSelector：实测在 IndexHNSWFlat 上它只过滤「图遍历 可达」的点 —— efSearch=64 探不到的子集成员直接丢失，400 条的用户只命中 1 条， 比不修还差。子集内的精确 top-k 只能穷举该子集，而这恰好很便宜。
    • 不额外建缓存：见上，直扫已经比现状快。
    • 单用户部署行为零变化：子集占全库超过 15%（_MAX_FILTER_SHARE）时不做前置 过滤，也不放大候选 —— 这种占比下全局候选里天然有足够多该用户的记忆。子集超过 10,000 条（_MAX_FILTER_SCAN）才退回全局检索并按 30 倍放大候选，并记一条 warning 提示排查超大用户。
    • 分数口径：前置过滤路径两侧都归一化后做内积（= 余弦），与 faiss 侧 normalize_L2 同口径，RRF 融合不受影响。
    • fts5_speedup_vs_like 这个指标本身不是有效的 FTS5-vs-LIKE 对照：它由本包的 soma/benchmarks.py 计算（定义见 :334，赋值见 :873，取值 = like_time / fts5_time），但两条基准查询跑的是不同的关键词集 ——
    agent.query_memory("第一性原理 系统思维", top_k=10)   # 两个 ≥3 字词 → FTS5 路径
agent.query_memory("思 系", top_k=10)                 # 两个单字词   → LIKE 路径

    本包内 FTS5 路径只处理 ≥3 字关键词（trigram 分词器的下限），LIKE 路径只处理 <3 字短词；生产链路是「FTS5 先跑，抛 OperationalError 才降级 LIKE」，没有 「关掉 FTS5 就更快」的开关。所以这个比值恒低于 1 是构造使然，不代表缺陷。 本版修复后它从 0.01 升到 0.15，但仍在 1 以下 —— 这不是残留问题。

    要用它做真实对照，两边必须跑同一批关键词（同库、同过滤、同 LIMIT、同 ORDER BY）。

    • generate_goals(user_id="") 仍是「系统级」混合语义 —— 这是有意保留的： 单租户部署（全部记忆都归属同一个用户，或根本不用 user_id）依赖它。多租户的 安全性不靠改这个默认值，而靠后台循环的 fail-safe —— 库里有多个用户却不配置 autonomous_background_user_ids 时，循环直接不产出目标。直接调用 generate_goals() 的接入方请自己传 user_id。
    • autonomous_background_enabled 仍然默认关闭，start_background() 未显式开启 时直接拒绝，不静默启动。
    • 上面那条修复只在「带过滤的检索」上体现：无 user/agent/时间条件时 SQLite 本 来就选 FTS 驱动的计划，两种写法一样快。所以单用户、不带过滤的基准看不出这个 缺陷 —— 它只在多租户（带 user_id）下暴露，正是接入方的生产形态。

    用本包自己的基准指标在 3,000 条 / 60 用户（带 user 过滤）上实测：

    指标 JOIN 写法 子查询写法
    fts5_avg_ms 12.11ms 1.04ms（11.7×）
    fts5_speedup_vs_like 0.01 0.15

    对照：同一份库不带 user 过滤时，两种写法都是 ~1.3ms，无差异。

    背景¶

    三条线索汇到这一版：

    1. 注入不带时间 —— 2.0.17 补的是「返回给调用方」的时间信息；SOMA 自己注入 LLM 的 prompt（四条注入路径）当时仍不携带时间。2026-08「失眠串台」事故的根因就在 这里：三个月前的状态记录被 LLM 当成当前状态。本次把这个缺口补齐，并把 2.0.13 / 2.0.14 两条「记入后续版本评估」的过时表述一并回填勘正。
    2. 认知循环只会单轮 —— loop() 是单轮闭环；run_autonomous() 虽能多轮，但目标 必须外部给，且没有常驻运行能力。
    3. 索引维护欠账 —— 记忆被删除时（forgetting 归档/清理、episodic.delete()）直接 删行、不通知 faiss 索引。残留向量既占 top_k 名额，又让删除后的首次搜索触发同步 全量重建（实测阻塞数秒）。

    多专家共享 SQLite 连接（soma/db.py）

    • 同一进程内指向同一 db 文件的 store 复用同一条连接，引用计数管理，减少文件句柄数 与 WAL 写锁竞争
    • 复用粒度是每个 db 文件、每个线程一条，不是「进程级一条」。CPython 的 sqlite3 即使 check_same_thread=False，并发使用同一条连接也会静默丢数据（实测 4×25 只落库 26~31 条）—— 这是刻意的设计约束，不是保守

    • transaction() 上下文管理器：异常回滚、正常提交，共享与独立两种模式都可用

    行为变化¶

    删除记忆后不再当场同步重建索引。 此前 similarity_search 一旦发现「DB 比索引少」 就全量重建（HNSW 数秒，阻塞搜索）。2.0.18 起改为：本次搜索按 stale 补偿取 k、调用方 过滤已删条目，清理交给后台剪枝。

    影响面：删除刚发生后，索引条目数会短暂大于 DB 有效数，直到后台清理完成。接入方 若断言两者立刻相等需调整（我们自己的两处测试已随之调整）。已删条目不会被召回 —— 这一点没有变化。

    对话 prompt 里会多出「可能已过期的状态记录」块。 当库里存在 nature=state 且超过 30 天未更新、且与当前问题有至少 2 个共同汉字的记忆时，SOMA 会把这些记录单独成块注入 （每次至多 2 条）。此前它们到不了 prompt，所以这是新增内容而非改写既有内容 —— 但 接入方若对 prompt 做逐字节快照比对，需要重新采集基线。_build_prompt(...) 的 stale_states 参数默认为 None，直接调用 _build_prompt 的既有代码行为不变。

    更正：共享连接的内存收益（2.0.18.1 回填）¶

    本节原先写「多实例指向同一库省约 151MB RSS（3 实例）」—— 该数字不成立， 现更正如下。接入方在生产实测只有约 18MB，他们的质疑是对的。

    正确口径：共享连接省下的是「同一个 db 文件被重复打开的那些连接」，每条连接 的 page cache 上限 8MB，所以收益上界 = 省掉的连接数 × 8MB，且只有缓存真正被读热 时才接近上界。实测（每个配置跑在独立子进程，增量从 import 后起算）：

    场景 共享关闭 共享开启 差
    3 实例 · 不写不读 +3.2MB +1.9MB 1.3MB
    3 实例 · 每实例写 200 条 +3.2MB +2.1MB 1.1MB
    3 实例 · 开向量搜索 +11.5MB +4.7MB 6.8MB

    接入方在 26,977 条记忆的生产库上实测约 18MB，与上表同量级。

    151MB 是怎么来的：那是把两种配置放在同一个进程里先后测量得到的 —— 进程 RSS 只增不减，后测的那个配置替先测的背了嵌入模型等懒加载资源的账。用同样 的错法重测，立刻得到 191MB / 233MB 量级的假差（tmp/measure_shared_rss.py 的 第一版就是这么写的，已改成每个配置独立子进程）。

    结论：这项优化的价值在文件句柄复用与写锁竞争的减少（接入方实测总 fd 28→16、 同库连接 4→2），不在内存。

    变更 / 所有权语义¶

    实例 close 时只释放自己创建的 embedder：

    场景 _owns_embedder close 行为
    SOMA(...) 自建 True 释放自己的 ONNX 会话
    SOMA(embedder=shared) 注入 False 不动 —— 由调用方管理

    这条规则是必需的：多实例共享一份 embedder 时，若实例有权释放，第一个 close() 的实例就会把其他实例正在用的会话打掉。

    Added¶

    • 因果推理引擎 (soma/memory/causal.py): CausalGraph 基于语义三元组构建因果链。find_root_causes() 回溯根本原因，get_causal_chain() 查找两节点间的因果路径。hub.causal_analyze() 在激活阶段自动追踪因果链路。支持环路检测与max_depth保护。
    • 记忆冲突检测 (soma/hub/_conflict.py): ConflictDetector 在激活管道中识别逻辑矛盾的记忆对（如"降价→流失"vs"服务质量→流失"）。两阶段检测：(1) 否定模式匹配（中英双语），(2) 谓词冲突（causes↔prevents等高冲突对）。冲突分数≥0.5的记忆对自动降权（×0.4惩罚系数）。批量ONNX编码（单次推理替代逐条）确保<100ms延迟。
    • 反向传播 (soma/hub/_core.py): _backward_propagate() — 高激活记忆（score≥0.4）的领域标签反向映射到思维规律，自动生成建议焦点。权重上限不超过任一直接触发规律的50%，防止偏离主线。
    • 跨域类比引擎 (soma/analogy.py): AnalogyEngine 基于结构签名（in_predicates + out_predicates的frozenset）发现不同领域节点的拓扑同构。当两个看似无关的概念共享相同的图结构时自动桥接。节点扫描上限500、图谱上限2000防止大图CPU过载。结构签名缓存（边数变化时自动失效）。引擎实例在MemoryCore中惰性缓存复用。
    • 反思质量评估 (soma/quality.py): QualityEvaluator 对LLM生成的推理输出进行三维评分（一致性、连贯性、可操作性），0-1分制。加权综合（一致性40% + 连贯性30% + 可操作性30%），输出质量等级（excellent/good/fair/poor）。低质量回答通过 needs_reflection 标记提示。

    思维框架深化 — 从"平铺列表"到"推理网络"¶

    v0.5.0 的核心主题是激活已有的 relations 字段，让 7 条思维规律从独立触发升级为协同推理网络。 同时引入认知偏差检测、确认偏误防御、问题复杂度自适应等机制，让 SOMA 的思考更接近真正的"智者"。

    Added¶

    • 规律链推理 (Law Chaining): WisdomEngine.decompose() 新增阶段2——当规律A的关键词命中问题时，其 relations 中的关联规律B获得权重加成（部分命中 ×0.50，纯链式 ×0.35）。利用 wisdom_laws.yaml 中已定义但从未使用的 relations 字段。

    • 动态权重调整步长: MetaEvolver._calc_step() 根据样本量自适应——≥15 样本 → 0.03，≥5 样本 → 0.02，<5 样本 → 0.01。替代原先固定 ±0.02 步长。
    • LLM 缓存可配置: SOMAConfig 新增 llm_cache_ttl（默认 600s）和 llm_cache_max_size（默认 50），替代 _call_llm() 中的魔法数字。

    • 反馈闭环修复: SOMA.respond() 和 SOMA.chat() 现在正确区分 LLM 成功调用与 mock 回退，outcome 不再无条件标记为 "success"。
