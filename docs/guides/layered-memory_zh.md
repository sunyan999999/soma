# 分层记忆（L2 场景 / L3 画像）运维指南

> 适用版本：**v2.0.24+**。本指南里的数字来自真实生产实测
> （162 用户、`uvicorn --workers 3`），不是实验室估算。

## 一、它是什么

SOMA 的记忆分三层：

| 层 | 内容 | 存储 | 产出方式 |
|---|---|---|---|
| **L1 情节** | 每条原始记忆 | `episodic.db` | `remember()` 直接写入 |
| **L2 场景** | 把多条相关记忆聚合成主题块 | `scenes.db` | 自动（攒够条数 + 冷却期后） |
| **L3 画像** | 从场景里提炼的用户特征（偏好/习惯/技能/知识盲区/目标） | `profiles.db` | 自动（场景数达到阈值后） |

L2/L3 都要调 LLM 做语义抽取，所以**有成本**、**默认异步低频**。

## 二、开与关

**默认开启**（v2.0.21 起）。显式关掉：

```python
s = SOMA(..., scene_extraction_enabled=False, profile_extraction_enabled=False)
```

关掉后**一次 LLM 调用都不产生**（有判据钉死）。

> ⚠️ 注意参数语义：`None`（默认）= 跟随 `SOMAConfig`；
> 传 `True` / `False` 才覆盖。

## 三、触发规则

### L2 场景

```
渐进预热：首次阈值 1（第一条记忆就产出场景）
        之后阈值 1 → 2 → 4 → 5 翻倍拉长
成本闸：  scene_min_interval 默认 300 秒
         —— 两次捕获之间至少隔 5 分钟（跨进程共享）
```

### L3 画像

```
场景总数 >= 上次触发时的场景数 + profile_scene_interval（默认 10）
→ 触发一次画像更新，并把标记推进到当前场景数
```

这是 **v2.0.24 修正后的语义**。旧版（≤2.0.23）是「场景数必须正好是 10 的
整数倍」，而实际增长序列是 8 → 13 → 19 → 25（每次捕获 3~8 条），每次都
跨过 10/20 —— **一次都不会触发**。如果你升级前画像是 0，升级后第一次
捕获就会补上。

## 四、成本（实测）

**单次成本**（deepseek-flash，162 用户生产环境实测）：

| 操作 | tokens | 金额 |
|---|---|---|
| 场景抽取 | 900 ~ 2,200 | **≈ 0.0016 元** |
| 画像更新 | 4,800 ~ 5,800 | **≈ 0.0049 元**（输出多，比场景贵约 3 倍）|

**按使用强度的估算**（每 5 条记忆 1 次捕获、每 10 次捕获 1 次画像）：

| 场景 | 单用户日成本 | 162 用户日成本 |
|---|---|---|
| **典型**：日写 10 条记忆 | ≈ 0.004 元 | ≈ 0.65 元 |
| **典型**：日写 20 条记忆 | ≈ 0.008 元 | ≈ 1.4 元 |
| **典型**：日写 100 条记忆 | ≈ 0.042 元 | ≈ 6.8 元 |
| **满负荷**：12 次/小时 × 24h | ≈ **0.5 ~ 0.6 元** | ≈ 81 ~ 97 元 |

> ⚠️ **「典型」和「满负荷」差 40~50 倍，不要混用。**
> 「满负荷」是理论上限（一个用户 5 分钟写一次记忆、全天不停），
> 实际几乎不可能达到。对外表述请分开写，否则容易被误读成「成本极低」。

参考：某生产环境今日全站 343 次调用 / 109.6 万 tokens / 2.457 元，
其中 L2/L3 占 **0.48%**。

## 五、监控

`get_layered_stats(user_id)` 返回：

```python
{
  "scenes": 33,                  # 场景总数
  "profile_entries": 33,         # 画像条目数
  "capture": {
      "enabled": True,
      "consecutive_failures": 0, # 连续失败次数
      "total_failures": 0,       # 累计失败次数
      "last_capture_time": 1794970959.8,
      "last_detail": {...},      # 进程内，见下
      "capture_lease": {         # 跨进程租约状态
          "in_flight_for_s": 0.0,
          "cooldown_for_s": 241.6
      }
  }
}
```

**告警组合（最重要）**：

```
total_failures 在涨  且  scenes 不涨   →  L2 在静默降级
```

典型原因：LLM key 失效、额度耗尽、base_url 配错。v2.0.23 起连续失败 3 次会
打 **ERROR** 级日志，不再只有一行 WARNING。

## 六、多进程部署（重要）

`uvicorn --workers N` 下每个 worker 各持一份 SOMA 实例。捕获的互斥与节流
**放在 `scenes.db` 的 `capture_lease` 表里**，天然跨进程：

| 字段 | 作用 |
|---|---|
| `in_flight_until` | 正在抽取中，防止多个 worker 并发抽同一用户 |
| `cooldown_until` | 捕获冷却期，等价于跨进程的 `last_capture_time` |
| `last_profile_at` | L3 画像阈值标记（v2.0.24+）|

- `force=True`（手动触发）跳过冷却，但**仍不能与正在进行的捕获并发**
- 进程崩溃留下的租约靠过期自愈（in_flight 180 秒）
- **不需要**额外的 flock / 文件锁，也不需要限制「只允许单进程启用」

> 升级前的行为：没有这张表时，三个 worker 会把同一批记忆各抽一次，
> 产出语义重复、措辞不同的场景（「信任体系与文化赋能」vs
> 「信任体系与企业文化落地」）。如果历史数据里有成对场景，可人工清理。

## 七、返回值语义

`capture_scenes()` 返回**本次实际新增**的条数。它可能返回 0 而库里已有数据，
因为：

- `remember()` 已经自动捕获过，本次提取的标题全部重复（`add_scene` 按
  同用户 + 同标题去重）

要判断成败，用 `get_last_capture_detail(user_id)`：

```python
{"extracted": 3, "created": 1, "skipped": 2, "reason": "ok", "error": None}
```

| `reason` | 含义 |
|---|---|
| `ok` | 有新增 |
| `no_new` | 提取到了，但标题全部已存在（去重）|
| `empty_extract` | LLM 没返回任何场景 |
| `locked` | 另一个进程正在捕获 / 还在冷却期 |
| `no_memories` | 该用户没有可用的近期记忆 |
| `no_provider` | 没接 `memory_provider`（老构造方式）|
| `provider_error` | 取记忆时抛异常 |
| `failed` | LLM 调用失败（`error` 字段有原因）|

> ⚠️ `last_detail` 是**进程内状态**。CLI 新进程调用返回 `{}` 属正常；
> 多 worker 下每个 worker 各记各的。监控请读当前 worker 内的值，
> 不要跨进程/重启后回查。持久化的只有 `capture_lease` 和场景/画像本身。

## 八、注入到 prompt 的体量

有硬上限，不会无限膨胀：

| 层 | 条数上限 | 附加过滤 |
|---|---|---|
| 场景 | `max(top_k // 2, 2)` | 必须命中前 5 个关键词之一 |
| 画像 | `top_k` | `min_confidence ≥ 0.3` 且必须命中关键词 |

默认 `top_k=5` 时最多 2 条场景 + 5 条画像。某生产环境实测：开启 L2/L3 后
注入中位 **621 字**，比开启前的 788 字**更短**（画像体量本来就小）。

最坏估计：全量注入约 +500 字 ≈ +750 tokens，相对聊天输入均值 3,200 tokens
约 **+23%**。若需收紧，可用两个现成旋钮：调小 `top_k`、调高
`ProfileStore.get_entries` 的 `min_confidence`。

## 九、基准测试注意事项

| 维度 | 重复次数 | 原因 |
|---|---|---|
| `wisdom` | 1 次即可 | v2.0.22 起 `decompose` 以问题文本定型，可复现（实测标准差 0）|
| `memory` | **至少 3~4 次取中位** | 受索引落定影响，实测只跑 2 次时出现过 40.7 的离群值（极差 46.3）|
| `overall` | 3 次取中位 | 受 memory 波动影响 |

另外：如果基准或评测跑在失效的模型配置上（key 过期 / 额度耗尽），务必把
**「模型调用失败」和「回答得 0 分」区分开** —— 否则失败会伪装成「某模型
能力差」，污染对比数据。
