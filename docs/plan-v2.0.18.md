# SOMA v2.0.18 开发计划

> 主题：**自主与稳固** —— 让认知循环真正自主，同时清掉积累的历史债。
> 制定日期：2026-09-13
> 基线：v2.0.17（948 测试通过；PyPI/GitHub 已发布）

---

## 一、版本目标

v2.0.17 解决了「单条脏数据崩全库检索」和「SQLite mmap 吃掉 811MB/实例」两个生产事故级问题。
v2.0.18 转向两件事：

1. **补上认知循环的最后一段** —— 现在的循环能力齐了，但它仍然等着人叫它；这一版让它能自己找到目标、自己跑起来、跑出来的东西能沉淀到后续会话。
2. **还清历史债** —— 文档里若干「留待后续」其实早已实现，几处版本号和基准分对不上，长期干扰判断。

外加一项来自接入方的实际诉求：记忆注入时带时间信息。

## 二、任务清单

### 任务 1：记忆注入携带时间信息

**现状（已核实）**

| 路径 | 位置 | 是否带时间 |
|---|---|---|
| `explain_activation`（对外 API） | `soma/hub/_core.py:234` | ✅ 已有 timestamp / age_days / memory_type / nature / is_stale（v2.0.12） |
| L1 轻量模式注入 | `soma/agent.py:530-534` | ❌ 只有 `content[:200]` |
| L2/L3 记忆参考注入 | `soma/agent.py:592-596` | ❌ 只有来源/关联度/content |
| 反面视角注入 | `soma/agent.py:607-611` | ❌ 同上 |
| 矛盾记忆注入 | `soma/agent.py:618-625` | ❌ 同上 |

接入方（DSH）报的「彦彦失眠串台」事故，症状是 LLM 分不清「昨天的失眠」和「三个月前的失眠」。
事故发生在**注入**环节，而 `explain_activation` 是返回给调用方的结构 —— 真正缺口在 `_build_prompt`。

**做什么**

- 四条注入路径全部带上时间标注，形如 `[参考1] (3 天前) …`、`**[参考 2]** (来源: X, 关联度: N, 12 天前)`
- `age_days` 小于 1 天的显示「今天」，避免出现「0 天前」
- **带上记忆类型**（episodic/semantic/skill）—— DSH 建议，对注入层有直接价值
- `is_stale=True` 的记忆附加一行提示：这是 N 天前的状态，可能已变化
- **口径与 `explain_activation` 对齐**：复用现成的 `age_days` / `timestamp` / `memory_type`，
  不另造名词（DSH 明确建议）
- `explain_activation` 保持不动 —— 上游字段已足够，不重复劳动

**验收**：构造「昨天的失眠」与「三个月前的失眠」两条记忆，注入出的 prompt 文本能明确区分二者时间。

**风险**：低 —— 纯文本增量，不破坏任何调用方。

**依赖**：✅ **已对齐（2026-09-14，DSH 回信 `resp-20260914-soma2018-timestamp-align`）**

DSH 自查后确认「**是他们误报**」：`explain_activation` 的 timestamp/memory_type 确为上游 v2.0.12 原生具备。
他们的补丁在上游已有同名字段的情况下插入了**重复键**，靠幂等标记写法不同（他们用 `getattr(...)`、
上游用 `mem.timestamp`）而干净打上，后写者遮蔽上游。他们已还原线上文件、给补丁加上游检测、
并修掉导致误报的误导性输出。

据此**本任务范围锁定为改注入层**，不为「新增字段」排期。DSH 支持此方案，且他们在
`mobile/api/routers/chat.py:892`、`mobile/api/routers/openai_compat.py:796/953` 直接调用
`agent._build_prompt(...)` —— 改完他们直接受益。

### 任务 2：多专家共享 SQLite 连接

**现状（已核实）**

代码里有 8 个 `sqlite3.connect` 调用点，全部 `check_same_thread=False`：

```
soma/memory/episodic.py:30    soma/memory/semantic.py:24
soma/memory/skill.py:21       soma/memory/scene.py:32
soma/memory/profile.py:38     soma/evolve.py:25
soma/analytics.py:22          soma/audit.py:28
```

`MemoryCore` 实际实例化 episodic / semantic / skill（scene、profile 按配置可选）。
mmap 已在 2.0.17 默认关闭，所以**内存影响已经消除**；剩下的收益是减少句柄数、降低写锁竞争。

**为什么做**：DSH 把实例池从 5 调到 10，单 worker 预计 ~2.1GB，连接数与写锁竞争随之上升。

**难点（这是本版风险最高的一项）**

SQLite 单连接多线程写必须串行化。更麻烦的是**事务边界**：现在每个 store 各自 commit，
合并成一个连接后，一个模块的 `commit()` 会把另一个模块未完成的事务一起提交 ——
**数据一致性风险**，这也是 CHANGELOG 当初写「留待有明确压测数据后再评估」的原因。

**做什么**

1. 先做设计验证：单连接 + 显式事务边界的可行性（写一个最小原型验证事务隔离）
2. 引入连接管理器：按 db_path 进程级共享 + 线程锁，每个 store 的写操作走显式事务上下文
3. **保留配置开关**：出问题可一键切回多连接模式
4. 与 DSH 要连接数 / 锁竞争的实测数据，作为收益依据

**验收**：连接数从 N 降到 1；多线程并发写下数据一致（无丢写、无串事务）；单条写入性能不劣化。

**风险**：**高** —— 涉及并发与事务边界，回归面大。放在本版最后做，留足测试时间。

### 任务 3：全自主认知循环彻底完成

**现状（已核实）**：能力齐了，但都是「被动」的。

- `soma/__init__.py:803 loop()` —— 单轮闭环，感知→推理→行动→反馈→进化，五阶段完整
- `soma/__init__.py:980 run_autonomous()` —— 多轮迭代，三种完成判断，实现完整
- 缺口：目标必须外部传入；不会自己启动；进化触发是硬编码的 `self._session_count % 5`；
  无 LLM key 时完成判断永远返回 False，只能跑满轮数

按你确认的四项验收标准，逐项落地：

**3a. 自主目标来源**
SOMA 自己从记忆与未完成事项中产生目标，不等外部给。
来源候选：`nature=state` 的长期未解决状态、含待办/计划语义的记忆、进化产生的待验证假设。
需要一套筛选与排序规则（重要性 × 时效 × 未解决程度），并保证不重复捡同一条。

**3b. 后台常驻自动运行**
定时或事件驱动自动跑循环，不需要外部主动调用。

> ⚠️ **安全设计（硬约束）**：SOMA 是本地优先框架，**未经明确许可自动跑后台循环是不可接受的**。
> 此项**默认关闭**，必须显式开启；开启后仍强制有：最大并发 1、CPU/内存上限、
> 随时可停、运行日志可查。绝不出现「装完自己烧 CPU」的情况。

**3c. 循环环节质量打磨**
- 进化触发改为基于洞察积累量，不再用 `% 5` 硬编码
- 完成判断增加本地启发式兜底，不依赖 LLM 也能做合理判断
- 失败重试 + 指数退避，失败原因记录可查

**3d. 跨会话记忆整合**
循环产出的洞察写入记忆（带 context 标记），确保后续会话能检索到，并触发进化 ——
形成真正的长期闭环，而不是跑完就散。

**验收**：四项各自有可验证的行为；持续运行一段时间无内存泄漏；后台循环可随时启停。

**风险**：中 —— 逻辑复杂但无并发风险（除 3b 的后台线程）。

## 四、交付流程

```
开发完成
  → 全量回归 + 生产数据实测 + 与 2.0.17 对比
  → 构建 wheel
  → 四重隔离检查（soma-agent 绝不入包：git ls-files / .gitignore / wheel / sdist）
  → 出安装包交 DSH 在生产环境实测
  → DSH 确认没问题
  → 推送：PyPI + GitHub tag + Release
  → 推送前再跑一次四重隔离终检
```

**硬约束**：推送的任何版本都不带 soma-agent。soma-agent 尚不是成品，将来要做成独立项目。
每次推送前的四重隔离检查必须全部通过。
